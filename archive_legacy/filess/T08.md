# T08 · How verified content survives three languages

**Type:** `wayfinder:grilling` (HITL) · **Module:** Data · **Blocked by:** ~~T06~~ · **Blocks:** T15
**Status: CLOSED 1 Sep 2026**

## Question (as asked)

Fifty schemes, four chunks, three languages ≈ 600 spoken strings. The lock says nothing is spoken that a human has not verified. Who verifies, and what exactly do they verify?

## Resolution

### 1. The arithmetic in the question was stale

Two things had moved since this ticket was written:

- **T06 changed the chunk count.** Read-back is `summary` (authored, ~35 words) plus four verbatim sections offered by keypad. `exclusions` is a Checker input; `gate_notes` are explicitly never spoken. Neither counts toward spoken load.
- **T04 changed N.** The 12 Sep corpus is deliberately small for testing ease. 50 was never the demo number.

Corrected shape of the load:

| Class | Volume | Nature |
|---|---|---|
| Verbatim chunks | 4 × N × 3 | Translated from English |
| `summary` | 1 × N × 3 | **Authored natively**, not translated |
| Aliases | variable | **Heard, never spoken** — ASR match targets, not TTS strings |
| Fixed lines | ~60–80 × 3 | One-time block, frozen, does not scale with N |

**Design N = 100.** Everything is planned and costed as if 100 schemes exist. The demo runs a small subset, chosen for testing ease per T04.

### 2. All three languages stay — because a language is now cheap

**Hindi, English and Marathi all ship on 12 Sep.** The acceptance bar is unchanged.

Marathi was briefly dropped in this session and then restored, and the reason matters more than the outcome. Marathi was only ever expensive because of the verifier — someone had to read Marathi well enough to sign that a sentence about money was true, and that person did not exist. Once verification is deferred (§6), **Marathi costs exactly what Hindi costs, which is nothing beyond machine time.** The justification for dropping it disappeared, so the drop went with it.

**Adding a language is about a day's work.** Nothing in the design is per-language logic. A language is a config entry plus two artefacts:

1. The keyword list rendered into that language (~150–200 values)
2. The scheme chunks and fixed lines run through translation and TTS at ingest

Both are batch jobs. No code changes, no new call path, no new prompt. This is what makes a fourth or fifth language a scheduling question rather than a design question.

### 3. Inbound flow: English pivot, closed-set exit

Ratified against the original design, which had no English in the call path:

1. Caller speaks Hindi, English or Marathi → Sarvam transcribes in the pinned language
2. Text translated to English internally
3. Agentic system reasons in English and **selects one value from a fixed keyword list**
4. That keyword is echoed back in the caller's language from cache
5. Caller confirms or corrects

**Why the English hop is safe here:** step 3 constrains output to a closed set. The model can be loose and the translation imprecise; the worst achievable outcome is the wrong item from a known list, never an invented sentence. An inbound error is recoverable — wrong filter, caught by the confirmation ladder, visible in the LOG.

**Step 4 requires no runtime translation.** The echo strings are the keyword values themselves ("Maharashtra", "farmer", "below poverty line") — the same ~150–200 values per language, written and cached once. The caller hears exactly which box was ticked, in their language.

### 4. Outbound read-back: unchanged

Pre-translated at ingest, cached as content-addressed audio, played back. **No runtime translation and no runtime generation on the outbound leg.**

The asymmetry is deliberate and is the load-bearing distinction of this ticket: an inbound error mis-files a caller and is recoverable; an outbound error speaks a false sentence about money a caller may be entitled to, which is an untruth and a structural call failure under T04. The two legs do not get the same rule because they do not carry the same cost.

### 5. The keyword base is the test harness

The closed keyword list, in all three languages, is the base the system is tested against. It is small — roughly 150–200 values across `state`, `occupation`, `category`, `gender`, age band, residence and the rest — written once and frozen.

It makes the inbound leg **testable offline**: a table of utterances mapped to expected keyword codes, run in CI with no phone call. A runtime-translation design with free-text output cannot be tested this way, because the matcher's input does not exist until the call happens. This is recovered from **T22**, which now feeds the Model module as well as Data.

### 6. Verification: deliberately deferred

**No human verifier is staffed.** The 12 Sep build is a hackathon deliverable, not a production system. Translation is done naively and shipped unverified.

This **suspends the truth lock** ("nothing is spoken that a human has not verified") for the demo. It is not repealed — it is a debt, recorded here, to be paid before any real caller depends on the output.

Consequences accepted:

- A mistranslated amount or eligibility line can reach a caller with no human in the path
- Under T04 that would be an untruth spoken, i.e. a call failure — the demo is exposed to a failure mode the original design excluded
- The system prompt must force keyword selection from the database rather than free composition; this is the only remaining guard, which makes **T11 load-bearing for the inbound leg**, not just for read-back

### 7. The staffing branch is void

The original ticket's questions about who signs off, per-string versus per-scheme sign-off, hold-aside checking and Marathi staffing are all downstream of a human verifier. With no verifier staffed, they do not resolve — they are deferred with the lock.

The hold-aside rule (scheme names, amounts, dates reinserted untouched after translation) **survives as a machine check**, since it needs no language skill: assert the held-aside tokens are byte-identical in input and output, and refuse the row otherwise. This is the one verification step that costs nothing and catches the worst failure (₹6,000 becoming ₹60,000). It stays.

## What this changes elsewhere

- **Acceptance bar:** unchanged — Hindi, English and Marathi all ship
- **T15** unblocked
- **T11** gains a hard constraint: the model selects from a closed set, never composes free text — now on the inbound path, not only read-back
- **T22** gains a second consumer: its value lists are the inbound test base
- **Truth lock** suspended for the demo, recorded as debt

## Default that was overridden

The stated default was machine-translate then one named human signs off per language per scheme, with Marathi dropping to Door A if sign-off could not be staffed.

The resolution went further on the verifier and the other way on Marathi: **no human sign-off in any language**, and **Marathi kept in full** rather than reduced to Door A. These are the same decision seen twice — dropping the verifier is what made the third language free.
