# C2 — deterministic scripted run

## What changed
- `Session.load_script(script)`: adopts the script's seed, clock origin, tick length and name, rewinds to day 0 and queues the events. Refuses (`RuntimeError`) while the run is streaming. `reset()` unloads the script and returns to the live configuration.
- Each tick first fires the events whose `day <= t_sim_days`, once, in day order: cave-in / tilt / crack through `events.to_failures` (appended to `pillar_failures`), vibration through `apply_vibration`. A row goes to `events.csv` for each (`collapse`, `tilt`, `crack`, `blast`).
- `events.csv` also gets a `node_alarm` row (`N22 CRITICAL`) whenever a node alarm is raised, in every run, not only scripted ones. This is how "the first alarm lands within one packet" is measurable in `events.csv`.
- `python -m sandbox.runner --script default_demo --out out/scripted/default_demo`: no broker, DB or backend. Writes `nodes.csv` and `events.csv` and prints their sha256.
- `POST /script/run {name}` on :8000: loads the script into the live session (idle, ready for `start`), sets the default speed (whole script in ~4 min). 409 while running, 404 unknown name, 422 invalid script.
- `/interventions` now tags each failure with `script_event` and returns `script_events`; FORGE's `/forge/seed` uses them, so a scripted crack seeds as one crack (not 39 cave-ins) and a tilt as a tilt.

## Decisions I made (the plan didn't cover them)
1. **`tick_seconds`.** At the live 60 s tick a 365-day script is 525,600 ticks: ~26 min offline, 1.7 GB of CSV, and the live loop tops out near 0.1 d/s, so the year would take over an hour. A script now sets its own tick (the demo: 3600 s → 8,760 ticks, 169 s offline, 29 MB). The packet window follows the tick (1 tick = 1 packet, as before). Events still fire on the first tick at or after their day, and all demo days fall on a tick.
2. **Scripted runs don't auto-snap to 10×** on a CRITICAL zone (`SessionConfig.auto_snap_speed`, default True elsewhere), or the speed would drop to 10 mid-run.
3. **TILT in the live engine.** `assign_node_states` treats a bowl like a cave-in, so a 5 mm/m tilt would have put its target node CRITICAL. `PillarFailure` gets `ring: bool = True`; tilt failures set it False, are skipped by the rings and judged by `assign_tilt_states` with the FORGE limits (WARNING ≥ 3 mm/m or strain limits, CRITICAL ≥ 10 mm/m).
4. "Within one packet of the event's (collapse) time" is measured from the event's day: the live engine starts alarming at `t_init` (the warning phase), not 8 h later at the collapse.

The live engine still forgets a cave-in or crack once its window ends; FORGE keeps it. So live shows fewer WARNINGs than FORGE (no N05 / N01 / N12 for the demo).
