# C3 — play the script through the live pipeline

## What changed
- New `scripts/run_scripted_demo.js` (`npm run demo:scripted [-- --speed N] [--name default_demo]`):
  1. Clears the database (`scripts/reset_demo_state.sh`, falling back to `POST :8080/api/system/reset`) — the script's clock is fixed, so a second run's rows would collide with the first's timestamps and silently vanish under `ON CONFLICT DO NOTHING`.
  2. Resets the engine (`POST :8000/control {action:"reset"}`), loads the script (`POST :8000/script/run {name}`), sets the speed (`--speed` is scripted days per wall second; default comes from the script's own `speed`), and starts (`POST :8000/control {action:"start"}`).
  3. Follows the backend WebSocket (`:8080/ws`) and prints a timeline as alarms arrive, batched per 300 ms window and attributed to the most recent non-vibration event at that alarm's day (`eventFor`), e.g. `day  60.0  crack      → N22 CRITICAL, N23 CRITICAL`. Vibration events are announced on their own line (`(moves no node state)`) since they never carry an alarm.
  4. Exits when the engine reports `health.script.done` or the sim day reaches `duration_days`, printing the final CRITICAL/WARNING node-alarm tally; Ctrl-C stops the engine and exits the same way.
- `sandbox/server.py`: the simulation loop now checks `session.script_done` every tick and stops the session itself once a scripted run reaches its duration, instead of drifting a year-and-a-day past it.
- `sandbox/server.py` `/health` reports `script: {name, duration_days, done}` when a script is loaded, `null` otherwise — this is what the demo runner and `qa.js` poll.
- `sandbox/server.py`'s WebSocket `set_speed` action now no-ops while a script is loaded: the 3D client sends its fixed 10x on every connect, which used to slam a scripted run's clock the moment a dashboard attached. `POST /control` (the demo runner's own route) is unaffected — only the WS message is gated.
- `sandbox/session.py` adds the `script_done` property (`t_sim_seconds >= script.duration_days * 86400`).
