# G1 — the real-anchored district, ported to sandbox coordinates

## What changed
New pure-maths module `simulation/sandbox/district.py`: the Adriyala LW1
fit (`constants.ADRIYALA_FIT` block, DOI 10.18311/jmmf/2022/32099),
superposed across a 3-panel district (`DISTRICT_PANEL_X_M`,
`DISTRICT_START_DAY`, `DISTRICT_PROVENANCE`), in sandbox coordinates
(x across strike, y along strike, face advancing +y).

The closed-form Knothe subsidence with time lag and inflection-point
offset (`_exp_erfc`, and the per-panel loop inside `physics.subsidence`,
lines ~30-145 of `sih-26-finale/mine-sim/src/minesim/physics.py`) is
vendored near verbatim, credited at each function. The coordinate map is
`finale_x = sandbox_y - FIT_FACE_START_Y_M`, `finale_y = sandbox_x`, with
`FIT_FACE_START_Y_M = -(WINDOW_SIZE_M/2 + FIT_R_INFL)` and
`FIT_R_INFL = H_DEPTH_M / FIT_TAN_BETA` (≈146.05 m) — the fitted-geometry
analogue of the existing `FACE_START_Y_M`/`R_INFL`.

`channels()` does not call `subsidence_m` five independent times for its
central differences: `_f_y` depends only on sandbox X and `_f_x` only on
sandbox Y, so shifting X by the 2.5 m step reuses the unshifted `_f_x`
(and vice versa). That halves the erf/erfc/erfcx calls against the naive
approach and is what keeps `channels()` on the full 241×241 grid under the
plan's 50 ms budget — see **Verify** below (20.3 ms measured, was 51.3 ms
before this optimisation).

`subsidence_mm`/`subsidence_m` accept `y_offsets_m`/`start_day_offsets_d`
overrides (default: the 3-panel district), the same parameterisation
`physics.subsidence` itself takes — used by the tests to evaluate LW1
alone against finale's own single-panel run.

**`constants.py`** gets an additions-only `ADRIYALA_FIT` block: the fitted
Knothe/seam numbers (`FIT_A_SUBS`, `FIT_TAN_BETA`, `FIT_C_KNOTHE`,
`FIT_M_SEAM_M`, `FIT_INFLECTION_OFFSET_M`, `FIT_FACE_ADVANCE_M_PER_DAY`,
`FIT_SOURCE_DOI`), their derived `FIT_R_INFL`/`FIT_FACE_START_Y_M`, and the
district layout (`DISTRICT_PANEL_X_M`, `DISTRICT_START_DAY`,
`DISTRICT_PROVENANCE`). Geometry (depth/width/length) is unchanged and
shared with the primary block — `H_DEPTH_M`/`W_PANEL_M`/`L_PANEL_M`
already equal the paper's 375/250/2500 m, so only the Knothe/seam numbers
needed adding. Nothing in the existing primary block or `surface.py` was
touched.

## Planner decision

The original check (d) (max |tilt(t)−tilt(0)| ≥ 3.0 mm/m for all 30
sensing nodes) failed for 3 nodes and left several more with margins
under 0.5 mm/m. Before reporting, I confirmed this was not an
implementation bug: `district.subsidence_mm` for the full 3-panel
district matches finale's own `physics.subsidence` **bit-for-bit** (max
diff 0.0 mm) at every sensing-node coordinate, at days 0, 90, 200 and
365, using finale's own `PanelGeometry`/`KnotheParams` from `load_config`
with `y_offsets_m=DISTRICT_PANEL_X_M`, `start_day_offsets_d=DISTRICT_START_DAY`
(`test_lw1_district_matches_finale_at_sensing_nodes`).

Planner's ruling (27 Sep): **keep `DISTRICT_START_DAY=(-120,0,120)` and
`layout.py` unchanged.** The plan's Context §3 ballpark ("all 30 sensing
nodes see ... tilt ≥ 3 mm/m") was measured as *absolute* tilt, not
*since-install* tilt — the two differ for two physical reasons, not
modelling errors:

1. **Early-panel pre-settlement.** `DISTRICT_START_DAY=(-120,0,120)`
   starts the x=-290 panel 120 days before the observed year begins.  By
   day 0 it is already ~90 days into its own effective mining
   (`t_k = 0 - (-120) - 2d/v ≈ 90.5 d`), so nodes over it have already
   absorbed part of its tilt before the "since install" baseline is
   taken. Re-staggering was measured (by the planner) and never gets all
   30 nodes to 3.0 mm/m (best min 2.55) — moving the stagger only moves
   which nodes are short, it doesn't remove the effect.
2. **Opposing slopes between bowls.** A node sitting between two troughs
   sees a real physical partial cancellation of tilt (the two bowls pull
   the ground in opposite directions), which is smaller in the vector sum
   than either bowl's tilt alone.

Since this is real (fitted) ground physics, not a bug, the plan's fixed
literal 3.0 mm/m bar for *every* node was the wrong acceptance test. Check
(d) is changed to two threshold-file-driven bars — ADVISORY (1.5 mm/m)
for all 30, WARNING (3.0 mm/m) for at least 27 of 30 — both read from
`config/alarm-thresholds.json` via `sandbox.thresholds.load()['conditions']['tilt_change']`,
never hard-coded, so the test tracks Segment T's table if it changes.

All 30 reach ADVISORY; 27/30 reach WARNING; 3 (14, 21, 27) stay at
ADVISORY on tilt alone.

**D1 decides final per-node alarm coverage from all conditions together,
not tilt alone.** Node 14 is tier 1B and carries a strain gauge (see
`layout.py`'s tier table) — its own strain reading, not just tilt, feeds
its alarm state; nodes 21 (1C, fault transect) and 27 (2A, router anchor)
likewise have other channels (1C carries strain; 2A is a router anchor
with its own subsidence/tilt reading, already at ADVISORY here) that D1's
per-node classification will combine with tilt_change. Three ADVISORY-only
nodes on tilt is not by itself a coverage gap — it's an input D1 has to
account for.

**Tilt rate is a non-issue for the bowl, as expected.** Measured max
daily tilt-rate magnitude across all sensing nodes, all consecutive days
in 0..365: **0.138 mm/m/d** (steepest at node 10, day 86→87) — comfortably
under the `tilt_rate` ADVISORY/WARNING thresholds (0.3 / 1.0 mm/m/day) in
`config/alarm-thresholds.json`. Those thresholds only fire on events
(a FORGE cave-in, a sudden face-arrival transient), never on the smooth
Knothe bowl — intended, per the planner.
