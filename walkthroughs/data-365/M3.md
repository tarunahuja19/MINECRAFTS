# M3 — remove fabrication

## What changed

- **Deleted the forced 6500/4200 µε strain floor and the crack-latch
  reset** (`session.py`). Two fabrications lived in the same block: a node
  at CRITICAL/WARNING state had its `strain_ue` channel force-floored to
  6500/4200 µε regardless of what the physics actually produced — even on
  tiers with no strain gauge at all, since the assignment ran unconditionally
  whenever `channels` was a dict — and `sensor_array`'s own crack latch
  (`node.crack_latched`) was reset to 0 on every tick a node wasn't
  CRITICAL, which is backwards: a real crack that has opened does not heal
  because the zone manager's state happened to drop that tick. Both are
  gone; `r.crack_flags` is now left exactly as `SensorArray.sample_tick`'s
  own strain-threshold latch set it, and `r.node_state` (the single source
  of truth for node colour) is unaffected — it was never derived from
  `crack_flags` or the fabricated strain floor to begin with.
- **Replaced the hard-coded trough-fit R², confidence and days-to-L3**
  (`mqtt_bridge.py`, two call sites: zone alarms and node alarms) with
  `null`. No trough-fit or forecast model exists anywhere in this codebase
  to back a claimed 0.94/0.88/0.95 R² or a 0.92 confidence — they were
  fixed numbers keyed only off the alarm `level`, never computed from an
  actual fit. `days_to_level_3` keeps its one honest case (`0` when
  already at level 3 — a tautology, not a guess) and nulls the rest,
  rather than inventing "3.5 days" or "3.0 days" with nothing behind
  either number.
- **The SNR boot gate's unit mismatch, investigated and fixed where it
  actually lives.** `session.py::_verify_boot_snr` combined
  `sigma_strain_ue` (microstrain) directly with a `delta_signal` computed
  from a strain peak documented as mm/m, a straight 1000x unit mismatch —
  now converts the peak to microstrain before combining, so both operands
  of `gates.snr_margin` are honestly in the same unit. This changes the
  number the boot line prints (6.98 -> ~6980) but not the boot decision:
  a 40-sample Knothe trend swamps the noise floor at either scale, and
  `gates.py`'s own gate (`MARGIN_THRESHOLD = 3.0`) is not sensitive to
  which of these two internally-consistent numbers it receives.
  `gates.py` itself, and `tests/test_session_a.py`'s `test_t48_snr_margin_*`
  tests, were deliberately left untouched: they test `gates.snr_margin`
  directly with their own inputs, reproducing the source plan's own
  published 6.81 (n=40) / 2.41 (n=20) figures, and `gates.py`'s docstring
  already carries a full, numerically cross-checked derivation of exactly
  those two numbers against the plan's frozen noise budget. That is a
  different, already-validated claim from session.py's own local variable
  handling, and nothing here changes it.

## Files
- `simulation/sandbox/session.py` — removed the strain-floor/crack-reset
  block; fixed the unit conversion in `_verify_boot_snr`.
- `simulation/sandbox/mqtt_bridge.py` — nulled the fabricated
  `trough_fit_r2`/`projection.confidence`/`projection.days_to_level_3` at
  both alarm-publishing call sites.
- `simulation/tests/test_session_c.py` —
  `test_t48_boot_refusal_on_high_noise`'s inflated `sigma_strain_ue`
  raised from 25.0 to 5000.0: with the unit fix, the margin the old value
  produced (371.88) no longer drops below the 3.0 threshold, since both
  the margin's numerator and denominator are now honestly ~1000x larger
  than the old mismatched pair. 5000.0 comfortably clears the new
  threshold-crossing point (~3100).
