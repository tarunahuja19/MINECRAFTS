# T1 — one shared alarm-threshold table, read identically by Python and Node

## What changed
The five files the plan asks for already existed on disk when this step
started (`config/alarm-thresholds.json`, `config/threshold_vectors.json`,
`simulation/sandbox/thresholds.py`, `backend/alarm/thresholds.js`, plus both
test files) — most likely from a run that was cut off before it reported.
This step checked each one against the brief line by line rather than
re-writing from scratch, and found one real bug plus one spec gap:

- **PPV band boundary bug.** Both `_ppv_band` (Python) and `ppvBand` (JS)
  picked a band with `freq_hz <= max_hz`. The brief says band selection is
  `freq_hz < max_hz` (max_hz exclusive), which also matches the DGMS table's
  own wording ("< 8 Hz", "8-25 Hz", "> 25 Hz") — a reading of exactly 8 Hz
  belongs in the 8-25 Hz band (limit 10), not the < 8 Hz band (limit 5). The
  old `<=` put an exact 8 Hz reading in the stricter band. Fixed in both
  `simulation/sandbox/thresholds.py:_ppv_band` and
  `backend/alarm/thresholds.js:ppvBand` to use strict `<`.
- **Missing `error_cases` in the vector file.** The plan asks
  `config/threshold_vectors.json` to carry `error_cases: [{condition}]` for
  the ValueError/throw conditions, so both languages assert the same list
  instead of each hard-coding `['comms_stale', 'sensor_flatline']`
  independently (the whole point of a shared vector file). Added the array
  and rewired `simulation/tests/test_thresholds.py::test_non_value_conditions_raise`
  and `backend/alarm/thresholds.test.js`'s throw-test loop to read it from
  the vectors file.
- **Added the 8.0 Hz edge case.** The plan explicitly asks for PPV band
  edges "7.9 Hz vs 8.0 vs 8.1 vs 30 Hz" in the vectors; only 7.9/8.1/30 were
  present. Added four `freq_hz: 8.0` cases (NORMAL/ADVISORY/WARNING/CRITICAL)
  — they now group with the 8.1 Hz cases (band limit 10), which is exactly
  the fix above made visible in the vector file: before the fix these would
  have failed against the stricter band-0 limit of 5.

Everything else in the four already-written files matched the brief on
inspection: JSON schema (`version`, `units`, `levels`, `conditions`,
`lifecycle`), every numeric threshold and `basis`/`description` string,
the Burland/BRE `categories` array on `crack_width`, the PPV `limits_by_band`
+ `fractions` structure, `comms_stale`/`sensor_flatline` as non-value
conditions that raise, and the `load()`/`classify()`/`crack_category()` /
`crackCategory()` API in both languages with identical rounding and boundary
rules (`value == threshold` reaches that level).
