## What changed

### Fix 1 — live feed self-starts from real state (no faking)

**Premise correction vs. the original task prompt:** the prompt described
Fix 1 as removing an inline `<script>` in `index.html` that fakes
`simulation-play` / a hardcoded `simulation-status RUNNING`. That script does
not exist in the current `index.html` — confirmed by grep and by `git diff`
showing no such addition. The real bug was different and is described below.

`dashboard_electron/renderer/js/data/mode-switch.js` — in `setMode('live')`,
`liveProvider.start()` was gated behind `window.__SIM_PLAYING__`, which used
to be set `true` by the PLAY button's `startPlay()` in `sim-tab.js`. That
button (and `startPlay`/`stopPlay`/`togglePlay`/the timeline) was already
removed by the prior B0 pass, so nothing ever set `__SIM_PLAYING__` true again
— `liveProvider.start()` never ran, and the live feed never started.

Investigating further (this is the deviation from the plan as written, noted
up front): `window.__SIM_PLAYING__` is not only a gate on whether
`liveProvider.start()` gets *called* — it is used as a pervasive internal gate
*inside* `live-provider.js`, `node-markers.js`, `sim-live.js`,
`status-bar.js`, `replay-controller.js` and `fixture-provider.js` to decide
whether to process telemetry/status at all. Removing only the outer gate (as
literally described) leaves telemetry permanently suppressed, because nothing
else sets the flag true. Confirmed by testing: simply removing the outer gate
still leaves `#sim-live-day-badge` at `LIVE · —` and the MAP tab node data
frozen.

The fix applied: in `mode-switch.js`'s live branch, set
`window.__SIM_PLAYING__ = true` and call `liveProvider.start()`
unconditionally when settling into LIVE mode. There is no header play/pause
control yet (step A3 adds one), so "in live mode" now simply means "the feed
is on" — consistent with the badge showing the *real* simulation state
(`RUNNING`/`STOPPED`) once the flag stops being force-false.

`liveProvider.start()` was checked for idempotency before deciding whether a
guard was needed in `live-provider.js`: it already has a `started` flag that
skips re-registering `window.r4` IPC handlers on a second call, and both
`connectWebSocket()` (checks `ws.readyState`) and `startSimHealthPoll()`
(checks `simPollTimer`) are already no-ops on repeat calls. No changes were
needed there.

The existing `bus.on('simulation-play', ...)` / `bus.on('simulation-stop', ...)`
listeners in `mode-switch.js` were left untouched (step A3 reuses them for a
header play/pause button). No fake `simulation-status` is emitted anywhere —
the real events still come from `live-provider.js`'s `handleSimulationStatus`
(WS `simulation_status` messages and the `:8000`/`:8080` health poll).

The LIVE badge (`#sim-live-day-badge`, already present in `index.html`) is now
driven from `dashboard_electron/renderer/js/sim/sim-tab.js`: a new
`updateSimLiveBadge()` polls `GET http://localhost:8080/api/simulation/status`
every 5s (the interval was already wired at `init()` from the prior pass, but
called a nonexistent `window.updateSimLiveBadge` stub — replaced with the real
fetch), computes `t_sim_seconds / 86400` to 1 decimal, and sets
`LIVE · Day <N.N>`, or `LIVE · —` on failure. There was no other/duplicate
polling implementation found elsewhere to consolidate. No tab-visibility hook
exists in `sim-tab.js` for gating this kind of poll, so it runs
unconditionally on the interval, matching the plan's fallback instruction.

## Deviations from the plan / discrepancies found

1. Fix 1's outer-gate-only description doesn't restore real telemetry by
   itself, because `__SIM_PLAYING__` is also used as an internal gate deep
   inside `live-provider.js` and four other modules. Fixed by also setting
   `window.__SIM_PLAYING__ = true` in `mode-switch.js`'s live branch — see
   the "Fix 1" section above for the full reasoning.
2. `verify_forge_isolation.js`'s blanket "`sim-tab.js` must never contain
   `:8080`" check now fails because of the explicitly-required LIVE badge
   fetch. Left un-edited (not in my permitted test-file list); flagged for
   the planner to either scope the check to writes only, or move the badge
   fetch to a module the isolation test doesn't cover.
3. `verify_sim_gate.js` tests the old manual-PLAY-gate design that this step
   intentionally replaces (self-starting live feed). Its failure is expected
   given the design change, not a regression to chase.
4. `verify_sandbox.js`'s CAVE-IN-trigger failure and `acceptance_s3.js`'s
   gate-banner failure are both confirmed pre-existing (reproduce identically
   with this pass's two edited files reverted) and unrelated to B0.
5. A pre-existing CSP gap was found while debugging check (b): `index.html`'s
   `connect-src` whitelists `ws://localhost:*` but not `ws://127.0.0.1:*`,
   so loading the dashboard via a `127.0.0.1` URL silently breaks the
   WebSocket (falls back to HTTP polling only). Not touched — out of scope
   for B0 — but worth fixing separately since some tooling navigates to
   `127.0.0.1` by default.
